TARS V2 SERVO SAFETY GATE AND CANCELLATION
===========================================

RUNTIME WRITE GATE
------------------
modules/module_servoctl.py validates every normal PWM command immediately
before the I2C write. A command is rejected when:

- The channel is not one of TARS channels 0 through 9.
- The pulse is non-numeric, non-finite, fractional, or outside 10 through 600.
- The pulse is outside that joint's configured and offset-adjusted envelope.
- Another thread owns the movement lock.
- The PCA9685 is unavailable or reserved for calibration.

If a saved joint position predates a calibration change and is already just
outside the new envelope, the runtime permits only successive values that move
that joint back toward the nearest calibrated boundary. It still rejects any
command that moves farther outward. This prevents the safety gate itself from
stranding an arm at an obsolete saved position.

The QML calibrator uses a separate explicit calibration gateway. Calibration
must be able to preview an offset before it is saved, so that gateway enforces
assigned channels and the absolute 10 through 600 range while the tester keeps
its existing endpoint checks and ramped writes.

CANCELLATION
------------
All delays in module_movements.py and the reset-position motion now use
wait_for_movement(). A voice, WebUI, or tester stop request wakes those waits
immediately instead of waiting through a three- or five-second pose.

Cancellation and unexpected movement exceptions release PWM centrally. This
prevents a partially completed gesture from leaving one or more servos powered
after its normal cleanup path was skipped. Controlled movement-specific return
to neutral remains a separate future milestone; the current stop is a prompt
motion abort followed by torque release.

PWM release is best-effort per channel: one I2C failure no longer aborts the
rest of the release loop, and failed channels are retried. A failed movement
write also attempts to release all outputs before the PCA9685 object is
discarded. Named movement presets receive a final torque-free check in their
shared wrapper. A persistent controller or wiring failure is reported as a
critical condition and still requires the physical servo-power switch.

No servo targets, gait phases, gesture speeds, or routine choreography were
changed by this work.

TEST COVERAGE
-------------
tests/test_servo_fake_hardware.py verifies invalid writes never reach fake
hardware, calibrated endpoints remain usable, calibration preview remains
possible, direct writes cannot bypass another movement owner, long legacy
poses cancel promptly, PWM is released after cancellation, and every registered
movement remains inside its calibrated envelope. It also covers transient
release failures, controller discard after a failed write, stale-position
recovery, and the complete handshake cleanup path.

CONTROLLED STOP VS. EMERGENCY POWER-OFF
---------------------------------------
A controlled stop (request_controlled_stop, including the voice/controller
"stop" action and the servo tester STOP buttons) sets the cooperative cancel
event. The active routine exits at its next motion checkpoint, releases PWM,
and gives up the movement lock. It does not latch the controller offline, so a
later movement may run normally.

An emergency power-off (emergency_power_off) does not wait for the movement
lock. It requests cancellation, immediately attempts to write zero duty cycle
to all PCA9685 channels, and latches every future PWM write and movement command
offline. The latch is cleared only by reset_emergency_stop, which first checks
the controller and confirms that outputs remain disabled. Resetting the latch
does not move or energize a servo.

"Power-off" here means PWM/servo torque release. Software cannot open the
physical power circuit. If the I2C controller is unreachable and the terminal
reports a CRITICAL release failure, use the rear hardware servo-power switch.

The QML servo tester exposes cooperative STOP separately from EMERGENCY OFF.
The WebUI Motion page provides CONTROLLED STOP, EMERGENCY OFF, and RESET
EMERGENCY LATCH controls. The historical /disable_servos endpoint now performs
the latched emergency action; /enable_servos resets it safely.

MOVEMENT WATCHDOG
-----------------
Every named movement and manually scoped WebUI servo session has an independent
watchdog. It triggers emergency power-off when either:

- The complete command exceeds movement_watchdog_timeout (45 seconds by
  default).
- One or more channels remain energized but no successful PWM write is seen
  for movement_stall_timeout (8 seconds by default).

The eight-second progress limit is deliberately longer than the longest
intentional static hold in the built-in movements (five seconds). The longest
built-in routine, happy_dance, has an estimated programmed duration of about
28.6 seconds, leaving substantial room below the 45-second total limit.

These settings are typed and validated in [SERVO]:

    movement_watchdog_enabled = True
    movement_watchdog_timeout = 45
    movement_stall_timeout = 8

The watchdog observes software execution and confirmed PCA9685 writes. Because
standard hobby servos provide no position feedback, it cannot prove that a
shaft physically reached its target. Mechanical stall detection would require
position feedback or a separately calibrated current-limit design.

EXPANDED FAKE-HARDWARE TESTS
----------------------------
The fake PCA9685 now supports persistent per-channel I2C failures. Tests cover
controlled cancellation followed by another successful command, emergency
latching and reset, refusal of writes while latched, best-effort release past a
permanently failing channel, watchdog progress stalls, watchdog total-runtime
limits, and typed watchdog configuration bounds.
